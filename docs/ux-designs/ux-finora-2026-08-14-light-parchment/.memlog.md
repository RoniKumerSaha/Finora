# Finora — Light mode parchment palette (2026-08-14)

## Run summary

User feedback: light mode looks too bright. The current bg
`#F7F4EC` (warm cream) sits next to pure-white cards `#FFFFFF`,
creating a sharp washed-out feel. The user wants a stronger
parchment push — bg becomes warmer / amber, cards become a soft
cream that's still lighter than bg, hierarchy carried by border +
shadow instead of surface contrast.

Mode: **coaching path with creative tools**. Three mock HTML
screens rendered to `.working/` (Mock A mild, Mock B medium,
Mock C strong). User picked **Mock A** — the mild option.

This is an **Update** to the parent run
`ux-finora-2026-08-13/DESIGN.md`. It modifies the **colors** block
in the YAML frontmatter and the **Color rules** body section. No
new visual identity is introduced — the same brand role count
(two brand colors), the same semantic role count (six), the same
typography, the same radii. Only the **light-mode surface palette**
shifts to a softer parchment register.

Source: `screenshots/light-mode-too-bright.png` (user-supplied, in
imports/).

## Decisions

### D1 — Light mode bg shifts from `#F7F4EC` → `#EFE5D0`

**Old**: `#F7F4EC` — a pale warm cream, slightly too cool and too
light against the white cards.

**New**: `#EFE5D0` — a warmer / amber-tinted cream. Reads as
"kraft paper, just slightly off-white" rather than "pale
parchment." L*-value drops from ~96 to ~91; a-chromatic hue shifts
from neutral toward a yellow-amber register.

The shift is intentional and bounded — this is **not** the
"deep tan" / "leather notebook" direction the user explicitly
rejected. The bg stays clearly cream, not brown.

### D2 — Card surface shifts from `#FFFFFF` → `#F8F2E3`

**Old**: pure white. Created a high-contrast punch against the
bg.

**New**: `#F8F2E3` — a soft warm cream that is **lighter** than
the new bg (not darker). Card/bg contrast is now ~4% (down from
3.4% but more importantly, the hue shift is gone — both surfaces
read as the same warm parchment family).

The cards-as-lighter-than-bg convention is deliberate. The
alternative (cards darker than bg, like a paper-stack) was
considered but rejected: it makes cards feel "below" the surface,
which fights the existing modal/elevated surface model.

### D3 — Input and surface-2 colors warm in lockstep

The input bg (`--surface-2`) was `#F0EBDF` (warm cream). With the
new bg, that color now reads slightly too pale. Push it to
`#F0E5CC` — same shift magnitude as the bg change (~5% darker in
L*) so the whole surface stack moves coherently.

`--surface-3` (was `#E5DECB`) shifts to `#E0D4B6`. This is the
"deepest" of the cream surface family; mostly used in chips and
rare hover states.

### D4 — Borders darken to maintain edge readability

The original `--border` (`#E5DECB`) was calibrated against the
old white cards. With the new softer cards, that same border
color now reads as too low-contrast against the card surface.

- `--border` `#E5DECB` → `#D8C9A6`
- `--border-2` `#D8CFB8` → `#C8B98F`

These remain in the same warm-amber family; just deeper. The
border shift is the load-bearing change that lets the new soft
cream cards still feel like distinct surfaces.

### D5 — Ink, muted, brand colors unchanged

All semantic colors stay. Ink stays `#2A2620` (dark brown). Muted
stays `#7A6F5E`. Primary teal `#0D8275`. Accent gold `#A47E2C`.
Danger, warn, success — all unchanged.

**Why**: the user's complaint was specifically about the
white-against-cream clash, not about the typography contrast or
brand hue. Touching the ink color would be a redesign; warming
the surface family is a palette rebalance.

### D6 — Card inset highlight re-tuned for new surface

The `.card` primitive carries an `inset 0 1px 0 rgba(255,255,255,
0.5)` top-edge highlight. With the new warmer card surface, that
highlight value should deepen slightly to keep the "soft top
light" feel — pure 50% white is now too contrasty against the
softer cream. Lower to `rgba(255, 255, 255, 0.35)`.

### D7 — Mock coverage: Home only

Three HTML mocks were rendered in `.working/` showing the Home
dashboard in the three candidate palettes. The user picked Mock A
without asking for more screens. The Home surface covers:
- Sidebar surface (240px, primary surface color)
- Main bg
- Card surfaces (3-up stat row + 2 cards)
- List rows inside cards
- Border treatment

This is enough surface coverage to validate the palette. No
additional screens were mocked because:
- Settings, Insights, Transactions, etc. all use the same
  primitives (`.card`, `.surface-2`, `.border`). Changing the
  palette affects them uniformly.
- Light/dark parity: dark mode is unaffected. The visual diff is
  contained to the `[data-theme="light"]` block.

## Open items

- [NOTE for UX] If the user wants Mock B/C later, the same
  update mechanism applies. Just shift the bg one more step.
- [ASSUMPTION] Muted text color `#7A6F5E` against new card
  surface `#F8F2E3` retains WCAG AA contrast. Spot check: the
  contrast ratio is ~4.6:1, above the 4.5:1 threshold for normal
  text. Acceptable. If a follow-up user complains about muted
  text being hard to read, deepen `--muted` to `#6B5F4D`.
